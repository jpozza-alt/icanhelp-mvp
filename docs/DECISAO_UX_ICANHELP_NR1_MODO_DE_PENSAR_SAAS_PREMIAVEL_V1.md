# DECISAO_UX_ICANHELP_NR1_MODO_DE_PENSAR_SAAS_PREMIAVEL_V1

Status: APROVADO  
Tipo: Decisao canonica de UX e produto  
Projeto: icanHelp NR-1  
Escopo: Workspace NR-1, jornada guiada, diagnostico, riscos, plano de acao, evidencias e revisoes  
Versao: 1.0  
Data: 2026-05-22  

---

# 1. Objetivo

Materializar como fonte oficial do projeto o modo de pensar de UX inspirado em referencias de SaaS e produtos reconhecidos por excelencia em experiencia do usuario.

Esta decisao nao trata de copiar telas, cores ou componentes de outros produtos.

Trata de consolidar uma mentalidade permanente para o icanHelp NR-1:

> Transformar um processo tecnico, normativo e especializado em uma experiencia guiada, clara, segura e orientada a decisao.

---

# 2. Regra-mae de UX

O icanHelp NR-1 deve funcionar como um assistente de decisao guiada, nao como um formulario tecnico.

O usuario nao deve sentir que esta preenchendo um PGR.

O usuario deve sentir que esta sendo conduzido por uma jornada que entende a realidade da empresa, organiza os riscos, mostra prioridades, gera plano de acao, guarda evidencias e mantem rastreabilidade.

---

# 3. Referencias conceituais

As referencias de SaaS/UX premiados entram como modo de pensar, especialmente a logica observada em produtos como:

- Pure CPQ
- Manager Hub
- produtos SaaS reconhecidos por simplificar fluxos complexos, centralizar decisoes e reduzir atrito operacional

Estas referencias devem orientar o raciocinio de produto, UX e interface, sem criar dependencia visual ou copia direta.

---

# 4. Principios derivados das referencias

## 4.1 Simplificar processos tecnicos complexos

O sistema deve esconder a complexidade operacional da NR-1, GRO e PGR na camada tecnica, apresentando ao usuario uma jornada simples.

Na frente, o usuario responde perguntas compreensiveis.

Por tras, o sistema estrutura:

- empresa
- estabelecimento
- setor
- atividade
- perigo
- risco
- grupo exposto
- controles
- plano de acao
- evidencias
- revisoes
- historico
- trilha

## 4.2 Transformar dados em centro de decisao

A workspace deve ser um centro de comando.

Ela deve responder rapidamente:

- onde estou
- o que falta
- o que e urgente
- qual e o proximo passo
- o que depende de evidencia
- o que precisa de validacao
- o que ja esta documentado

## 4.3 Reduzir duplicidade visual

Se uma informacao ja esta clara na sidebar, ela nao deve ser repetida como card no topo.

Se uma metrica nao ajuda a decidir, ela deve ser rebaixada ou removida.

A interface deve evitar:

- cards repetidos
- blocos concorrentes
- excesso de indicadores
- varias chamadas para a mesma acao
- visual de dashboard generico

## 4.4 Priorizar proxima acao

Toda tela principal deve deixar evidente a proxima acao recomendada.

Exemplos:

- cadastrar empresa
- selecionar estabelecimento
- mapear setores e atividades
- iniciar diagnostico
- revisar risco
- criar plano de acao
- anexar evidencia
- concluir revisao

A pergunta central da tela deve ser:

> O que o usuario deve fazer agora?

## 4.5 Esconder complexidade sem perder rastreabilidade

A linguagem principal deve ser humana e operacional.

Termos tecnicos devem aparecer apenas quando necessarios ou em camada secundaria.

O sistema pode falar em:

- sobrecarga
- prazo
- postura
- repeticao
- apoio da lideranca
- conflito
- evidencia
- acao
- responsavel
- prioridade

A camada tecnica preserva:

- tenant_id
- estabelecimento_id
- historico
- audit trail
- versao
- fundamento
- inventario
- plano de acao
- criterios
- revisoes

## 4.6 Workspace como assistente guiado

A workspace nao deve parecer uma colecao de formularios.

Ela deve parecer um espaco de orientacao e decisao.

A estrutura ideal e:

- topo institucional claro
- status de salvamento integrado
- sidebar enxuta de progresso e navegacao
- bloco principal de proximo passo
- conteudo detalhado apenas quando necessario
- alertas e pendencias com hierarquia
- linguagem simples e segura

# 5. Regras praticas para telas NR-1

## 5.1 Topo

O topo deve conter:

- identidade do modulo
- titulo claro
- subtitulo curto
- autosave alinhado como elemento de confianca operacional

O topo nao deve conter:

- cards repetidos da jornada
- excesso de metricas
- varias chamadas concorrentes

## 5.2 Sidebar

A sidebar deve servir para:

- navegacao
- progresso
- etapa ativa
- checklist resumido
- orientacao de continuidade

A sidebar nao deve virar:

- segundo dashboard
- duplicacao dos cards do topo
- deposito de texto tecnico

## 5.3 Area principal

A area principal deve priorizar:

- proximo passo
- decisao necessaria
- pendencia relevante
- acao objetiva
- informacao que reduz incerteza

## 5.4 Cards

Cards devem existir para organizar decisao, nao para decorar a tela.

Cada card deve responder a uma finalidade clara:

- informar
- decidir
- agir
- revisar
- comprovar

## 5.5 Autosave

O autosave deve ser tratado como componente de confianca.

Ele deve indicar que a jornada esta protegida e que o usuario nao perdera o trabalho.

Nao deve parecer um card solto ou desalinhado.

---

# 6. Relacao com identidade visual aprovada

Esta decisao deve respeitar a diretriz visual oficial do icanHelp NR-1:

- premium institucional
- SaaS limpo
- linguagem humana
- azul-marinho como base de autoridade
- off-white/bege claro como fundo
- branco quente em cards
- dourado suave apenas como acento
- nude como apoio humano
- salmao apenas como acento emocional pontual

Regra importante:

> O dourado nao deve ser botao principal. O botao principal deve permanecer azul-marinho.

---

# 7. Criterios de aceitacao de UX

Uma tela do modulo NR-1 so deve ser considerada boa quando responder sim para estas perguntas:

1. O usuario sabe onde esta?
2. O usuario sabe o que fazer agora?
3. A tela evita duplicidade?
4. A linguagem e compreensivel para usuario nao tecnico?
5. A complexidade tecnica esta escondida sem perder rastreabilidade?
6. O autosave transmite confianca?
7. A interface parece um SaaS institucional, nao um formulario bruto?
8. A tela ajuda a decidir, e nao apenas a preencher?
9. A hierarquia visual esta clara?
10. A jornada se aproxima de um produto premiavel em UX?

---

# 8. Anti-padroes proibidos

Evitar:

- formularios longos sem orientacao
- cards repetidos
- dashboards coloridos genericos
- excesso de slate/cinza frio
- botoes principais dourados
- jargao tecnico na camada principal
- tela que exige conhecimento previo de NR-1
- informacao documental sem contexto de decisao
- autosave escondido ou solto
- menu lateral poluido
- metricas sem acao associada

---

# 9. Frase canonica

> O icanHelp NR-1 deve seguir a mentalidade de produtos SaaS premiaveis: simplificar processos tecnicos complexos, transformar dados em decisao guiada e fazer o usuario sentir seguranca para avancar sem depender de jargao.

---

# 10. Impacto imediato na workspace NR-1

A workspace NR-1 deve evoluir para:

- menos duplicidade
- mais hierarquia
- mais clareza de proximo passo
- autosave integrado ao topo
- sidebar como navegacao e progresso
- area principal como centro de decisao
- visual premium institucional
- linguagem mais humana
- menos aparencia de formulario tecnico

---

# 11. Regra de governanca

Toda mudanca futura de UX no modulo NR-1 deve ser avaliada contra esta decisao.

Se uma alteracao deixar a tela mais tecnica, mais duplicada, mais poluida ou menos orientada a decisao, ela deve ser recusada ou revista.

---

# 12. Seguranca operacional

Esta decisao nao autoriza alteracoes automaticas em:

- banco
- RLS
- tenant
- auth
- .env
- secrets
- deploy
- producao

Qualquer implementacao tecnica continua seguindo:

- uma acao por vez
- PowerShell-first
- validacao PASS/FAIL
- evidencia em _debug
- sem commit, push ou deploy sem etapa propria
